RCA Agent 评测：开源方案与 STAROps 的同一评测集对比​

报告范围

本报告基于 RCA-100(RCA-Bench 当前版本数据集，103 个故障用例、28 类故障类型)评测集，分析生产环境 RCA Agent 在实体一致性、调查路径和结论复核三方面的工程能力缺口。报告同时给出两组实测结果：开源框架在Agent Framework、工具层语义化程度上的分数变化，以及 STAROps 通过 UModel(跨域实体归一化框架，把 APM / K8s / 云资源等域的实体映射到同一主键，21 类实体 + 4 类关系)、多阶段管道和结论复核带来的改进幅度。

评测口径

本文所有主结果均使用 RCA-100 分层评测集、相同任务输入和 brise 综合评分器。brise 是 RCA-Bench 配套的综合评分程序，按实体定位 E、故障类型 F 和调查过程 P 三个分量折算综合分 O，具体口径见评测基准 §5.2。因此，同一章节内的横向分数具备可比性。

本文比较的是两类 RCA 工程实现：一类是通用 Agent 框架接入 RCA 工具，另一类是包含 UModel、多阶段管道和结论复核的 STAROps 工程系统。该比较不用于给单一框架或模型排序，重点观察实体对齐、证据路径控制和结果可信度判断对 RCA 效果的影响。

根因诊断的起源​

RCA 任务的基础问题
一次生产故障调查不是单次查询。无论由 SRE 还是 Agent 执行，都要先确定告警指向的对象，再选择指标、日志、trace、拓扑等证据路径，最后判断结论是否足够支撑处置或复盘。本文后续的实验与系统设计都围绕这三件事展开。
期望中的诊断系统
理想的 RCA 系统在工程上需同时满足三项要求：第一，跨域实体使用统一命名，降低 Agent 的重复学习成本；第二，单次调查失败可在阶段级别检测并降级；第三，诊断结果产出可学习的结构化标签，支撑后续训练。任一项缺失，自动调查在首类失败时即退化为人工排查。本节阐述上述三项要求的工程含义，具体落地方案见 §4.1。
业界 RCA 工具的现状与局限
业界 RCA 工具的演进可分为四代。第一代以事件聚合为核心，解决告警风暴归并问题，但不输出根因。第二代为单栈 APM，提供应用层指标，但受限于单一数据源。第三代为拓扑推理，使用因果图与 trace 异常检测替代统计相关[1][2]，但拓扑构建依赖人工。第四代为 2023 年起的 LLM 直答方案，推理交由模型完成，引入幻觉与可用性问题。STAROps 在此基础上，将工程沉淀统一到统一实体层与多阶段调查管道。

RCA Agent 工程能力缺口分析​

面向生产环境的根因诊断任务，Agent 需要连续完成对象识别、证据采集和结论复核三类工作。结合 RCA-100 评测过程和典型生产链路，本章将通用开源 Agent接入 RCA 场景时暴露出的能力缺口归纳为三类：跨源实体一致性不足、调查路径稳定性不足、结论可信度判断不足。

能力缺口一：跨源实体一致性不足
生产环境的观测数据分散在 APM、日志、metric、trace、拓扑、变更和告警等系统中。同一服务在不同系统内可能分别表现为 service 名、pod 名、instance id、hostname 或 调用 span 名。若 Agent只能依据原始字段查询，每接入一种数据源都需要重新建立命名对应关系；一旦实体识别发生偏差，后续故障类型判断和证据链组织也会受到影响。
能力缺口二：调查路径稳定性不足
RCA 不是一次性问答，而是按顺序选择证据、验证假设并逐步收敛的过程。Agent 需要决定优先查询指标、日志、trace 还是拓扑，并在中间证据不足时继续补充调查。单层自由调用方式容易出现三类问题：数据源选择偏差、证据链中断和结论过早收敛。已验证经验能否复用，则取决于是否有稳定的实体关系和标准调查路径作为支撑。
能力缺口三：结论可信度判断不足
Agent 给出根因后，系统仍需判断该结论是否具备足够证据支撑。模型自评容易偏高，仅依赖关键词或固定阈值拦截又难以覆盖新故障类型。缺少独立复核信号时，每条 RCA 输出仍需要人工重新核验证据，自动化诊断带来的效率收益会被复核成本抵消。

开源 Agent 框架 RCA 实测结果​

本章在固定模型与评分口径的条件下，对开源 Agent 框架在 RCA-100 上的表现进行实测分析。实验重点考察两类工程变量：一是Agent Framework差异对综合分的影响，二是工具层语义化程度对实体定位的影响。同时结合 token 用量、调用轮数和总耗时，分析资源消耗与诊断质量之间的关系。

实验设置
本章采用控制变量方式开展对比实验。Agent Framework 维度固定 qwen3.6-plus 与 PaaS 工具集，仅替换 Agent 的调查组织方式；工具层维度固定模型设置，比较 IaaS 与 PaaS 两类工具入口。IaaS 指面向原始基础设施与观测资源的入口，通常按 pod_id、instance_id、SLS 日志或 CMS 指标等原始标识查询；PaaS 指面向服务和实体语义的入口，在工具调用前先把 service、pod、instance 等命名映射到同一实体。图 3-3 中的 PaaS-AI 是 PaaS 工具层的扩展配置，在 PaaS 的实体语义入口基础上增加 AIOps 算子。两组实验均使用 RCA-100 与 brise 综合评分器，分数具备本章内横向比较条件。
模型能力会影响证据阅读、工具调用规划和结论收敛，但本章不开展模型横向实验。为避免归因混淆，本章只分析Agent Framework和工具层语义化程度两个工程变量；后文评估 STAROps 时，继续围绕实体建模、阶段化调查和结论复核三个组件展开。
Agent Framework 维度实验
在同一模型和同一 PaaS 工具集下，5 个开源框架的综合分从 23.13 到 48.74，跨度 25.61 分。ReAct[11]、Multi-Debate[12]、OpenClaw 处于第一梯队，Reflexion[13] 与 Plan-and-Execute[14] 明显落后。过程分 P 的差异较小，五个框架均位于 0.53 至 0.60 区间；综合分差距主要由实体定位 E 和故障类型 F 拉开。
工具层维度实验
工具层实验用于衡量同一类 Agent在不同数据入口下的表现变化。参考阿里云可观测 MCP Server[15] 的工具集划分，本文将直接访问 SLS/CMS 等底层观测数据的入口记为 IaaS，将通过云监控 2.0[16] 或实体语义层访问服务对象的入口记为 PaaS。5 个框架汇总后的综合分由 IaaS 的 25.29 升至 PaaS 的 37.74，提升约 12.45 分，涨幅 49%。ReAct、OpenClaw、Multi-Debate 从 IaaS 切到 PaaS 后均有明显提升；Plan-and-Execute 出现反向下降，说明语义化工具需要与调查编排配合，不能自动修正早期路径选择错误。
框架与工具层交叉分析
交叉分析将效果、成本和延迟放在同一组开源方案下进行观察。图 3-3 对比实体命中与故障命中，图 3-4 对比 token 用量、总耗时与 E/F/P 贡献，图 3-5 将总耗时拆分为调用轮数和单轮耗时。结果表明，开源方案的主要限制不是算力消耗不足，而是实体命中、故障判定和调查路径控制未能同时保持稳定。
实验小结
在固定模型与评分口径后，开源方案的主要差距集中在三方面。第一，Agent Framework会显著影响结果，但仅替换框架不能稳定补齐故障类型 F；第二，从 IaaS 切换至 PaaS 可以明显改善实体定位，但语义化工具需要与调查编排配合；第三，token 用量、调用轮数和总耗时不能直接等价为诊断质量，高成本路径如果没有带来更好的实体命中和故障判定，只会增加延迟。
上述结果为后续系统设计提供了边界条件：STAROps 的效果不宜解释为单一模型或单一框架带来的增益，而应围绕实体建模、阶段化调查和结论复核三个组件分析。§4 将进一步说明这三类组件如何分别对应实体命名、调查路径和结论可信度问题。

STAROps 对三类能力缺口的工程应对​

本章承接 第二章对三类工程能力缺口的归纳，逐项说明 STAROps 的工程应对方式：跨源实体一致性不足由 UModel 统一实体与关系图谱予以收敛；调查路径稳定性不足由多阶段调查管道予以拆分约束；结论可信度判断不足由结论复核组件予以独立评分。三个组件分别覆盖实体、过程与结果三个环节，在 第五章同一评测集对比中共同支撑综合分的提升。

总览：三类能力缺口与三个应对组件的对应关系
工程应对策略概述
STAROps 将 RCA Agent 的工程能力分解为三个相互独立、可分别检验的组件：UModel 负责跨源实体与关系的统一，多阶段管道负责调查过程的组织与失败降级，结论复核负责对最终输出进行独立可信度判别。三组件不构成简单的工具堆叠，而是按实体—过程—结果的纵向链条依次承接，前一环节的产出构成后一环节的输入约束。
组件间的依赖关系
UModel 同时承担两项职能：其一为对 Agent 暴露按实体语义查询的工具接口，直接化解能力缺口一；其二为多阶段管道提供 SOP 路径检索所需的实体与关系基础，构成对能力缺口二的间接支撑。结论复核位于输出端，在 Agent 完成调查后对报告与轨迹给出独立评分，作为生产入库前的兜底门禁。三组件的对应关系详见图 4-0。
能力缺口一应对：UModel 统一实体模型
设计目标
UModel 旨在解决跨源观测数据中同一物理对象在不同子系统内呈现为多套命名的问题。具体目标包含两项：一是将 APM、日志、metric、拓扑、变更、告警等域内的对象统一收敛到同一实体主键之下，消除 Agent 因命名差异引发的重复查询；二是在统一实体之上建立显式关系图谱，使 Agent 可沿依赖、基础设施与变更链路扩展调查范围，而非在多个监控系统之间手工拼接查询条件。
数据范围与结构
UModel 当前版本覆盖上述 6 个数据域，共计 487 个实体与 1，005 条关系，实体类型涵盖服务、Pod、节点、主机、数据库、变更等运维核心对象。关系类型包含调用依赖、容器宿主、运行承载、变更绑定等结构性边，支撑由告警实体出发沿因果链回溯故障传播路径的检索需求。
工具入口设计
UModel 对 Agent 暴露按实体语义查询的 PaaS 工具集，替代原始 IaaS 工具层按 pod_id、instance_id、SLS 日志或 CMS 指标等资源 ID 查询的方式。Agent 通过 entity-call 一次请求即可获取服务的黄金指标，无需在多个监控系统间拼接查询语句与反向映射 label。U-SPL 一行查询与传统 PromQL[17] 多步拼接的对照详见图 4-1。
实测效果
在固定 Agent Agent Framework与 LLM 模型的对照条件下，5 个开源框架汇总后的综合分由 IaaS 工具入口的 25.29 提升至 PaaS 工具入口的 37.74，绝对提升 12.45，相对提升 49%(详见 第三章 图 3-2)。上述提升的工程根源在于实体命名歧义在工具层被提前消化，Agent 围绕同一对象的重复查询大幅减少，调查路径在调用源头即可获得稳定的实体锚点。本节成果由 第五章同 评测集 同 评分器 对比进一步支撑。
能力缺口二应对：多阶段调查管道
设计目标
面对云原生系统的复杂依赖，自由式 LLM 调查会把「探索证据」和「生成结论」混在同一轮推理里，任何早期路径错误都会直接传导到最终结论。多阶段管道把这两个动作显式拆开，让每一阶段的产出在进入下一阶段前接受独立校验，避免薄证据被一路放行。
三层机制协同
管道在调查环节由「拓扑遍历、必检清单与路径手册」三层机制协同推进，分别约束「查哪里」「查什么」「怎么查」三个问题。三层不是替代关系，而是叠加在同一轮迭代里共同起作用。具体协作关系见图 4-2。
两档调查强度
管道按 Fast 与 Deep 两档强度运行。Fast 模式面向告警清晰、目标实体明确的故障，几轮迭代即可收敛；Deep 模式面向排查空间更大、因果链路更复杂的故障，允许更深的拓扑遍历与更大的观测范围，代价是更长的诊断时间。两档共享同一套三层机制，差异只在迭代轮次与观测范围的上限。
收敛与降级
调查仅在证据闭环时收敛：嫌疑范围内的必检维度已覆盖、嫌疑方向切换后再走一轮新范围、关键实体的检查分支已闭环、Trace 类证据均已做属性差异与时段对比。任一条件未满足，管道触发降级而不是继续生成结论。同模型条件下，多阶段管道相对单层 ReAct 取得的综合分提升，工程根源即在于上述过程约束。本节成果在 第五章 Agent Framework 维度差距的拆解中得到支撑。
能力缺口三应对：结论复核
设计目标
结论复核位于 Agent 输出端。在诊断结论入库前，从方法论层面再过一道关，避免「看到症状就下结论」的浅层诊断进入处置流程。复核不打综合分，而是核对排查动作是否到位、证据是否扎实、机制因果是否成立。
质量保障机制
复核机制覆盖整个排查链路的关键节点，从拓扑顺序、Trace 深度分析、上游归因、工作负载稳定性、探针失败深因到最终结论规范化，每一个环节都设有强制检查，确保 Agent 不会跳过必要的验证步骤。具体检查环节如图 4-3 所示。
证据质量原则
自动化诊断最怕「看似有道理但经不起推敲」的结论。复核机制围绕四条核心原则核对每一份诊断报告的证据质量，确保结论可被复盘、可被审计。
对 Trace 类证据，复核会追问四个问题：谁先失败、怎么失败、为什么失败、是否为传播症状。任一问题答不上，该 trace 不能作为根因证据使用。

STAROps 与开源方案的同一评测集对比​

评测口径：主对照使用 RCA-100 30 个案例分层评测集、相同任务输入和 brise 综合评分器。开源侧选取当前实测最优配置 OpenClaw + DeepSeek-V4-Pro，STAROps 取同一评测集前 3 次重复实验聚合。该口径保证主分数、三维分量和故障大类差距可以横向比较。

本章比较完整 RCA 工程系统与通用开源 Agent 方案在同一 RCA 任务上的差异。图 5-1 用于观察故障类型上的分布形态；图 5-2 至 图 5-4 分别给出故障类型、评分分量和故障大类三个层面的差距。

总分对比
同一评测集主对照中，STAROps 综合分为 75.23(中位数 79.50)，OpenClaw + DeepSeek-V4-Pro 综合分为 51.02(中位数 53.42)，差距为 24.2 分。后续拆解显示，差距主要集中在实体定位 E 和故障类型 F，调查过程 P 的差距较小。
开源侧已经采用当前实测最优配置，包含框架、工具层、模型和运行参数的组合优化。因此，24.2 分差距不宜归因于单一模型或单一框架。补充实验显示，在固定任务、工具和评分口径后，不同前沿模型之间约有 10 分综合分差距，低于本节主对照差距。
图 5-2 · 10 类故障的差距分布
10 类故障的差距分布
按 10 个故障类型比较 STAROps 与 OpenClaw + DeepSeek-V4-Pro 的平均综合分。slowSQL、nodeCpuHigh、replicaScaleDown 三类差距最大；cpuFullLoad、trafficSurge 接近持平；rateLimiting 中 STAROps 低于对照组 18.9 分。
结果解读：差距在故障类型之间并不均匀。slowSQL、nodeCpuHigh 等需要跨服务依赖证据组合的场景，与 Eadro[6] 对微服务故障难度的观察方向相近，也更能体现实体关系和调查路径约束的作用。trafficSurge / cpuFullLoad 接近持平，可能与 QPS 突增、CPU 100% 等强症状信号较易识别有关。rateLimiting 中 STAROps 低于对照组，提示限流类故障仍需要补充外部策略、上游状态和边界观测信号。
差距拆解
24.2 分总差距按 brise 三个分量拆解为：E(entity 实体定位)+0.372、F(fault type 故障类型)+0.247、P(process 过程质量)+0.052。按 O = 40E + 30F + 30P 折算，对应 14.9、7.4、1.6 分。权重敏感性检查显示，在合理权重范围内 STAROps 与对照组的相对排序保持稳定。
实体定位贡献最大，原因在于 RCA 的证据读取依赖对象一致性。根因实体一旦偏移，后续日志、APM、metric、拓扑和变更证据都会围绕错误对象展开，并进一步影响故障类型判断。
将 30 个案例按评测案例的故障大类归并为 5 类后(节点、资源、流量、数据库、代码)，STAROps 与 OpenClaw + DeepSeek-V4-Pro 的差距为：数据库 +50.6、节点 +29.9、代码 +27.6、资源 +24.2、流量 −11.2。数据库、节点、代码和资源类为正向差距；流量类低于对照组，主要受限流场景影响。
流量类结果给出了当前版本的适用边界。上游 API 限流、DNS 解析异常、CDN 回源问题、第三方证书变更、云厂商区域性异常或公网链路抖动，通常需要外部依赖关系、合成探测、供应商状态页和网络边界观测共同支持。STAROps 当前优势主要体现在数据库、节点、代码、资源等内部可建模场景；外部依赖场景仍需补充外部实体建模和边界观测信号。
启示
本节结论不是开源框架排名，而是说明 RCA 专用工程组件对同一任务口径下的分数有显著影响。UModel 处理跨域实体翻译，多阶段管道约束证据收集路径，结论复核提供结果可信度信号。
从 brise 三个分量看，差距主要来自 E 和 F。生产 RCA Agent 的关键投入不是让模型生成更像专家的文字，而是让系统稳定完成实体归一、证据路径选择和结论复核。
该结论有明确适用范围。STAROps 当前优势主要集中在内部可建模故障大类；流量类，尤其限流场景，仍需补充外部依赖建模和边界观测。实际接入时应先核对用户故障构成，再判断预期收益。

边界、复现与后续验证​

本章说明当前评测结论的适用范围、复现条件和后续验证安排。本文所有分数结论均依赖指定评测集、评分器和任务输入，不能直接外推到未覆盖的故障大类、生产流程或其他 Agent 运行环境。

开放验证与社区复现

本文以 5 个开源Agent Framework在相同评测集上的对比为依据，结果应作为方向性证据使用，不作为最终统计结论。复现实验需要固定四项条件：同一评测集、同一案例元数据、同一任务输入和同一 brise 评分器。RCA-100 数据集已公开，外部方案可以在相同口径下提交 Agent 执行框架、模型和工具层配置，用于横向对比。

后续复现应补充三类统计信息：更大规模评测集下的置信区间，不同抽样方式下的重采样稳定性，以及单案例多次运行的方差。只有在这些信息齐备后，故障大类级结论才适合从方向性比较升级为稳定结论。

执行框架 × 前沿模型交叉评测

初步实验显示，在固定 RCA-100 评测集、brise 评分器和工具设置后，不同前沿模型之间约有 10 分综合分差距。模型能力仍然影响证据阅读、跨步骤推理、工具调用规划和结论收敛，因此不能从当前实验中剔除模型因素。

同时，模型差距不足以解释全部系统级差异。STAROps 与 OpenClaw + DeepSeek-V4-Pro 在同一评测集主对照中的差距约为 24 分，高于已观察到的模型差距量级。该差距需要继续拆分为三部分：模型能力、Agent 执行环境能力、RCA 专用工程组件能力。

后续交叉评测将扩展两个维度：一是 Codex、Claude Code 等代码与工具调用型 Agent 运行环境，二是 GPT、Claude、Qwen、Gemini 等模型系列。评测设计应保持案例、工具层和评分器固定，逐项替换执行环境与模型，以区分 UModel、多阶段管道、结论复核、执行环境和模型本身的贡献。
