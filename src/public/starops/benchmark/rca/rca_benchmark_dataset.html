序言

事故响应是生产运维的关键环节，工程师须在多套监控系统之间反复切换完成诊断。近年来，以运维数据分析为基础的方法开始不断发展，例如AIOPs强调利用人工智能手段解决运维的问题。但是，由于数据分析方法的局限性，导致RCA（Root Cause Analysis）任务在准确性、泛化性、可解释性等方面存在短板。最近，RCA Agent（根因分析智能体）不断涌现，这类智能体以大语言模型为推理底座，具备自主工具调用与多步推理能力，在接入告警后自动调用日志、指标、链路、变更等观测数据源，沿服务依赖与因果关系回溯异常传播路径，输出结构化的根因诊断结论与证据链。RCA Agent 自动接入告警与诊断输出环节，由工程师集中履行诊断结果的可信度判定。

摘要

RCA Agent 评估的任务形态较文本问答与代码生成更复杂，差异体现在输入动态性、观测主动性与因果可追溯性三个维度。评估对象是持续运行的分布式系统：输入随时间变化，Agent 须自主选择观测对象，并跨多源观测信号沿服务依赖回溯异常传播路径。仅以日志片段与根因标签构造的离线样本不承载主动观测过程，也无法区分诊断结果是真正定位至根因还是仅与告警表象相吻合。另外，需要区分定因结果是猜测获得还是推理获得。RCA-Bench 对应的主流参照工作分别为 Microsoft Research 于 MLSys 2025 提出的 AIOpsLab[1]，侧重在线环境与多任务能力评估；ICLR 2025 发布的 OpenRCA[2]，基于静态观测数据构建；面向 Kubernetes 域数据的 Cloud-OpsBench[3]。本文提出RCA-Bench 将 RCA Agent 评估分解为三项要素。其一，可产出真实故障信号的运行环境，依托阿里云仿真环境与故障注入机制，向 Agent 提供可查询的在线环境。其二，配备结构化基线真值的故障样本集合，首批覆盖 28 类、103 个故障实例，配套统一实体模型 UModel 与因果链基线真值。其三，将 Agent 输出映射为可比较分数的评估协议，定因与定界两维完全基于图距离规则评分，LLM 评判仅承担过程维度评分中的辅助判定，以支撑评分结果跨厂商、跨评分器复现。现行 RCA-100 数据集已支撑跨多个 RCA Agent 的对比评测。在 30 个子用例分层评估子集上，调优配置上限配置（基础模型 deepseek-v4-pro）综合分 62.10；默认开源配置（react 与 paas 组合）综合分 48.74；两档差距 13.36 分。

第一章 RCA-Bench 的提出背景

本章概要

从工业 RCA 痛点 → RCA-Bench 三要素框架 → 数据集核心挑战的动机闭环。

§1.1 RCA-Bench 的提出动机

RCA-Bench 提出的直接动机是 RCA Agent 能力测算落后于其在生产环境中的部署速度，缺少智能体能力量化机制。

§1.2 RCA-Bench 数据集的三要素

参考LLM Agent Benchmark的成功案例，RCA Agent的能力迭代需要一个具备运行环境、标准数据集、评测协议的RCA Bench。三要素的重要性在于每一要素负责 Agent 评估中一个不可代偿的职责：环境给数据动态性，样本给基线真值，协议给评分函数；缺其中任一要素即无法构成可比较的能力度量。同代 LLM Agent 基准（如 AIOpsLab [1]）普遍采用该框架，与 RCA-Bench 的差别不在三要素的拆分方式，而在每一要素内部的实例化决策。该框架适用于 Class B 同代 LLM Agent 基准，不覆盖 Class A 经典算法基准（无独立 Agent protocol）与 Class E 微服务测试床（无独立基线真值结构）。

§1.3 RCA-Bench 数据集的核心挑战

本节列出 RCA-Bench 在构造数据集时面对的四类核心挑战。这些挑战同时是同代基准的共性短板，并非 RCA-Bench 独有：RCA-Bench 与同代基准的差异不在难点本身，而在如何回应这些难点。本节难点取自 RCA-Bench 数据集构造视角，即 RCA-Bench 团队在数据集与评估协议两层可解决的部分。

1.3.1 传播链隐蔽

RCA 的根因实体与告警表象之间通常隔着一条因果传播链。以一次 MySQL 慢查询为例，根因信号首先在 MySQL 侧体现为查询耗时升高，再传导至调用方服务的端到端响应时间上升，最终在前端表现为 5xx 告警。该链路至少包含三类实体，分别为真正的根因实体、中间的传播节点与终点的告警实体。若数据集仅记录"告警发生在哪个服务"，评分函数将无法区分 Agent 给出的答案命中根因、命中中间节点抑或仅命中终点告警；三类实体在评分图距离上被压缩至同一位点。该难点是定界评分失真的根源。

1.3.2 主动观测

Agent 须自主决定观测策略：优先查询告警实体抑或优先调取调用链、沿调用链向下追溯抑或先查 Kubernetes events、一次性拉取全量上下文抑或逐步验证假设。观测选择本身即任务的组成部分。该选择若由预设规则承担，即退化为传统监控的流程编排；由 LLM 在运行时承担，方构成 Agent 任务。若数据集将时间窗口与关键日志预先截取交给 Agent，该维度在评估中被实际抹除。OpenRCA [2] 采用此类静态观测样本形态，主动观测能力不能在该数据集上度量。

1.3.3 实体标识割裂

同一物理对象在不同观测系统中具有不同名称。在应用性能监控（Application Performance Monitoring, APM）域中通常称为 Service，在 Kubernetes 域中表现为一组 Pod，在云资源（ECS）层中则呈现为 node 或 instance。该差异即业内所称的实体跨域映射问题，与 OpenTelemetry Resource Semantic Conventions [8] 所规范的统一资源标识属同一问题域。缺乏统一实体标识时，定界评分只能依赖字符串匹配或人工判断，评分不稳定、不可复现、不可审计。一套可用的 RCA Agent 数据集须先解决实体归一化，才能在其之上讨论定位评分。

1.3.4 基线真值标注成本与单点偏差

构造层三难点解决"数据集能否承载诊断过程评估"，治理层难点解决"基线真值本身能否被可信地建立"。专家人工标注 RCA 用例的成本通常达人天级别，单条事故复盘须经证据梳理、因果链确认与多轮交叉校验；标注规模一旦突破百级，专家人力即成为瓶颈。单点标注同时面临偏差不可控的问题：单一专家的领域经验、对故障类型的认知偏好、对因果链的剪枝习惯均会引入系统性偏差，跨标注者的偏差难以通过事后审核完全消除。该难点属于"数据集治理层"缺口，与 SWE-bench 对照不直接浮现（SWE-bench 的基线真值由单元测试客观判定，无标注成本）。

§1.4 RCA-Bench 简介

RCA-Bench 是面向 RCA Agent 的评估方法学，依托"运行环境、故障样本集合、评估协议"三要素框架，对 RCA Agent 能力开展可比较、可复现、可审计的度量。当前实例化数据集为 RCA-100，规模与结构含三层：用例层 103 条故障用例、覆盖 6 大类故障目录与 28 类独立 故障类型；实体层 UModel 21 实体类型与 4 关系类型，单用例中位 227 实体与 258 边，框架容量含 6 个域；可观测原始数据合计 3.46 GB、共 113,660,093 条观测记录。

第二章 RCA-Bench 的相关工作

本章概要

工业实践与同代基准对照，SWE-bench 框架下识别五项系统性缺口。

导读RCA-Bench 在 LLM Benchmark 参照谱系、RCA 同代基准、工业 RCA 实践、跨领域 Agent 基准四组参照对象中占据可识别的差异化位置：在 LLM Benchmark 参照谱系的方法学根基上叠加 RCA 任务面的四项增量、在 RCA 同代基准的 13 维对照中填补 6 维集中缺口、在工业 RCA 实践与基准评估之间保持职责边界、在跨领域 Agent 基准生态中以「领域内做深加方法学输出与借入」双向定位。这一定位是本章的论证主线。

§2.1 工业界 RCA 实践与基准评估的不对称

本节论证基准评估与工业 RCA 实践的职责边界：基准评估是评估工具而非生产系统，二者在错误成本上 存在系统性差异。工业界 RCA 实践在 SRE 与 AIOps 两个相邻概念层共同展开，RCA 是两者的共同任务面：SRE 团队承担事故响应工作流与 postmortem 知识沉淀，AIOps 提供异常检测、告警关联、根因定位的算法与工具支撑。RCA-Bench 由阿里云 AIOps 团队建设，评估对象是 AIOps 工具层的 RCA Agent，沿用 SRE 范式定义的事故响应工作流作为外部约束。本节论证基准评估与工业 RCA 实践的职责边界：基准评估是评估工具而非生产系统，二者在错误成本上 存在系统性差异。工业 RCA 实践在 SRE 与 AIOps 两个相邻概念层共同展开，RCA 是两者的共同任务面：SRE 团队承担事故响应工作流与 postmortem 知识沉淀，AIOps 提供异常检测、告警关联、根因定位的算法与工具支撑。RCA-Bench 由阿里云 AIOps 团队建设，评估对象是 AIOps 工具层的 RCA Agent，沿用 SRE 范式定义的事故响应工作流作为外部约束。

2.1.1 工业 RCA 实践的四层分布

工业 RCA 实践沿方法论层、流程层、工具层、厂商内部系统层四层分布。方法论层指事故响应方法学与学术参照，以 Beyer 等 [10] Site Reliability Engineering、Atlassian Incident Handbook [16]、Sambasivan 等 [18] NSDI 2011 request-flow comparison 为代表；流程层把告警聚合作为 RCA 前置环节，代表系统为 PagerDuty Intelligent Alert Grouping [17]；工具层覆盖 observability 平台内置 RCA 模块与独立 AIOps 套件，代表系统含 Datadog Watchdog RCA [19]、Splunk ITSI、New Relic AI、Dynatrace Davis、Honeycomb BubbleUp、Moogsoft、BigPanda；厂商内部系统层指厂商自有生产 RCA 系统，代表系统含 Google Dapper [9] 之上的内部 RCA 栈、Microsoft DeCaf [20]（在两个大规模云服务上诊断 10 个已知问题与 31 个未知问题），以及 Meta FBLearner 与 SCARF。

2.1.2 生产与基准的错误成本差异

生产 RCA 与基准 RCA 的错误成本存在着系统性不对称。生产环境中，诊断错误的下游代价含 MTTR 延长、错误修复操作执行、事故升级、用户感知扩大四类，单次错误可能产生小时级业务损失，因此生产 RCA 系统在评分协议层面自然偏保守：宁可输出"无法定位"或"建议升级人工"，不轻易给出未充分支撑的根因结论。基准环境中，诊断错误的代价收敛为评分扣分，单次错误的边际成本与单次正确的边际收益对称，故基准评分协议的隐含取向偏向"猜得准"：未输出候选的弃权策略与输出错误候选的扣分策略在多数评分函数下不可区分。

§2.2 同代 RCA Agent 评估基准的横向对照

横向对照对象沿附录 D.2 参照谱系。主对照面 5 套 LLM Agent 基准（AIOpsLab [1]、OpenRCA [2]、Cloud-OpsBench [3]、AnoMod [4]、SREGym [21]）维持 13 维深度对照；扩展对照面 10 余套 RCA 基准、数据集、测试床按 5 大类组织作 7 维更广概览。主对照入选须同时满足三项条件：发布时间在 2025 年至今、各自代表一种典型方法学取舍、数据与论文公开可复现；Eadro [7] 因发布时间为 2023 年不入主对照面，转入扩展对照面（详见附录 D.2）。扩展对照入选标准放宽至 2013 年以来与 RCA 评估直接相关的数据集、算法基准、工业竞赛、微服务测试床四类。

第三章 RCA-Bench 的总体设计与运行环境

★ 核心要点三要素框架（运行环境 / 数据集 / 评估协议）+ 四项核心设计回应 §2.3 五项系统性缺口 + 一项治理层延伸缺口；首批实例化为 RCA-100 数据集。
导读RCA-Bench 由运行环境层、数据集层、评估协议层三类组件与一条评估生命周期贯通线构成完整评估方法学。本章先给出整体架构视图与四项核心设计概览，再依次展开运行环境层的四项基础约束、被测系统拓扑、背景流量基线、Agent 可见的观测信号面。四项核心设计回应表 2-3 五项系统性缺口与一项治理层延伸缺口，具体实现下放至第 4 章与第 5 章。

§3.1 RCA-Bench 整体架构

RCA-Bench 的整体架构由四个要素构成：三类组件（运行环境层、数据集层、评估协议层）按数据流串联，外加一条评估生命周期贯通线把单次评估的环境预检至稳态验证组织为可复现的固定流水。三类组件的职责与所属章节见表 3-1。

§3.2 核心设计概览

RCA-Bench 沿定界（根因实体定位）、定因（故障类型分类）、过程（调查过程合理性）三维独立度量且彼此正交，按权重 [0.4, 0.3, 0.3] 合成综合分。三维分解相对同代基准（AIOpsLab [1]、Cloud-OpsBench [3]）的单维通过率保留部分正确诊断的中间得分粒度，与生产环境中 SRE 对 Agent 输出按"故障类型是否对、根因实体是否落在可操作粒度、推理过程是否可信"的多轴评价方式一致。该设计回应任务定义缺口与主动观测难点。

§3.5 背景流量

运行环境须持续注入背景流量。RCA 诊断的判定依据来自故障前后的对比变化，缺乏稳定基线时，Agent 无从判断某项指标的上升属于故障引发的异常还是系统原本即处于该水平。背景流量在 RCA-Bench 中承担三类作用：其一，保证业务链路持续产生调用链与指标信号，使 Agent 在故障注入前即获得完整观测面；其二，确保故障传播在服务调用链上真实发生，而非停留于被注入实体内部；其三，为 Agent 提供故障前后的对比窗口，使诊断推理具备时间基线参照。

3.5.1 双层调制策略

恒定速率背景流量只能产生瞬断型告警，无法模拟高峰期资源劣化或潮汐流量下的资源争抢，亦抹除了流量模式作为诊断线索的价值（例如"故障仅在批处理窗口出现"本身即可作为定因依据）。RCA-Bench 采用双层调制：第一层在总量上按时间曲线调节并发用户数，真实形成并发压力，而非在请求层丢弃流量模拟降压；第二层在结构上将单一用户类拆分为多个业务角色，各角色独立配置权重，使流量构成贴近真实业务分层。两层调制仅作用于入口链路，下游服务由上游调用自然产生流量，避免嵌套调制导致链路比例失真。业务角色与流量特征配置见表 3-5。

第四章 RCA-Bench 的数据集

本章概要

故障注入流水线 + 因果链基线真值 + UModel + GSTO 质量门禁全栈。

本章覆盖数据集层：先给出数据集构造的工程基础，再展开两项核心设计。

§4.1 数据集工程基础

数据集层须先建立两项工程基础：故障注入流水线产出候选用例、用例结构定义将字段打包为可评估的结构化对象。两项均为核心设计二落地所需的工程支撑。完整故障目录、用例 JSON 完整结构与难度分级框架在附录 A、C 展开。

4.1.1 故障注入流水线

RCA-Bench 采用注入驱动路线：先定义故障注入计划，再由真实系统自然产生观测信号。该路线的基线真值成本低、信号真实，代价在于故障覆盖受注入能力约束。OpenRCA [2] 等静态遥测样本基准放弃主动观测能力以换取标注便利；AIOpsLab [1] 等纯在线环境保留真实性但限制批量复现；RCA-Bench 在二者之间以可控注入换取大规模可复现的真实观测。

4.1.2 用例结构定义

用例结构定义（Case Schema）将基线真值、UModel 实体集合、运行环境产生的告警、时间窗口、可用查询语句封装为单一结构化对象，作为数据集层的统一数据契约。该结构化对象同时服务三类使用者：Agent 从中获取诊断输入、评分器从中提取比对基准、数据集维护者据其进行治理与筛选。一条合格用例的字段结构由七个维度构成，具体见表 4-2。

§4.2 结构化数据基础

数据集层须满足两项结构化约束。其一，因果信息以 因果链承载，含故障类型、根因实体、传播路径、证据检查点四类字段，配 C0 至 C3 链位置编码。其二，实体信息以 UModel 跨域归一化框架承载，每条用例配套一份告警时刻的实体与关系子图快照，覆盖 21 实体类型与 4 关系类型，单用例中位规模 227 实体与 258 边。OpenRCA 的扁平标签、Cloud-OpsBench 的推理轨迹、AIOpsLab 的 Kubernetes 自有 ID 均未将实体归一化升级为评分前置层。

4.2.1 因果链基线真值的结构设计

OpenRCA [2] 等同代基准采用扁平标签形式（例如 `root_cause = Inventory-Service`），仅可支撑传统分类或排序任务的评估。RCA Agent 评估须同时覆盖故障类型、实体定位、因果方向与证据查证四个维度（详见第 5 章）。RCA-Bench 将基线真值升级为结构化对象，至少包含四层，见表 4-4。

4.2.2 UModel 跨域实体归一化框架

实体跨域映射问题与 OpenTelemetry Resource Semantic Conventions [8] 处于同一问题域，在 RCA-100 中的具体形态为：Agent 输出 `Inventory Pod`，APM 侧为 `apm.Service:Inventory-Service`，Kubernetes 侧为 `k8s.Pod:Inventory-7d8fdc-xxxxx`，云资源层为 `cloud.node:cn-hongkong.xxx`。仅依靠字符串匹配时，Agent 输出 Inventory Service 与 Inventory Pod 是否命中根因完全取决于评分器的模糊规则，更换一套规则即更换一个分数，评估结果跨评分器不可复现。统一实体模型（Unified Entity Model, UModel）将散落于不同域的名称映射至同一主键，使定界评分具备确定性基础。

§4.3 数据集质量治理：质量门禁

候选用例从产出到入库须串行通过三层门禁：GSTO 自动检查、多智能体审核（核心设计四）、SRE 采样确认。三层为前置后置关系，任一层失效即传导至下游层并影响数据集可用性。

4.3.1 GSTO 自动检查

GSTO 自动检查作为质量治理的第一层，缩写对应四个串联校验维度：语法（Grammar）校验字段完整性、F 编号有效性与基线真值标注规范；信号（Signal）校验注入实际生效且预期传播路径在观测信号中可见；时间窗口（Time window）校验窗口起止合法且长度落在可评估范围；开放与回放就绪（Open and replay readiness）校验快照、拓扑、难度标签与脱敏信息齐备，支撑第三方独立复现。样本状态在 candidate、pending\_review、approved、rejected、deprecated 五种之间流转，三层流水示意见图 4-3。

4.3.2 多智能体审核

多智能体审核以多个独立 LLM 对同一条用例的基线真值做交叉审核，通过共识机制过滤单模型偏差，回应人工标注成本高与单点偏差不可控两项瓶颈。该思路在机器学习评估领域已有先例（例如 RewardBench [6] 用于偏好打分）；RCA-Bench 将其作为 RCA Agent 评估基准的基线真值审核机制与数据集质量治理的第二层门禁。协议为 N=3 跨厂商 LLM 独立审核与共识投票，存疑用例转入人工分流。

4.3.3 SRE 采样确认

GSTO 与多智能体审核均属机器审核，存在多模型一致同意一条看似正确、实际不可诊断用例的可能。SRE 采样确认作为质量治理的第三层，承担人工兜底职能：每批新入库样本按 15% 至 20% 比例随机抽检，对高难度用例（L3、L4 难度，分级定义详见附录 B）与多智能体共识一致率较低的用例做提权抽检；新增故障类型的前 5 条用例全部审核。审核沿五个维度展开：故障分类准确性、根因实体正确性、因果链完整性、指标数值真实性、结论一致性。

本章概要

§5.1 评估工程基础：任务定义与输出契约

评估协议的工程基础须满足四项约束。其一，任务输入须明确定义，Agent 启动时收到的字段集与字段语义在冻结快照内不变。其二，工具规范须显式列出 Agent 可调用的查询接口及其返回结构，未列入的接口视为禁用。其三，输出契约须强制三维结构化输出：`root_cause_type`（cause 维度）、`root_cause_entities`（boundary 维度）、`reasoning_trace` 与 `evidence`（process 维度）四字段缺一即视为无效提交。该契约是三维独立打分的前置条件。其四，禁用信息须显式列举，一旦在 Agent 上下文中检出即触发合规门禁。

§5.2 评估维度分解

三维评分函数遵守以下规则。其一，三维（cause / boundary / process）须独立评分并按公开权重合成；任一维度不得被折叠或被另一维度部分替代。其二，三维之间须经实测验证正交，Pearson 相关系数须低于 0.7 才视为合格。其三，各维度 `match_level` 函数（Cause 权重向量、Boundary 衰减函数、Process 子分权重）在 RCA-100 v1 冻结快照内 commit；后续版本变更须在 release notes 中显式声明并随附敏感性 ablation。

5.2.1 Cause Score（定因评分）

定因评分判断 Agent 给出的故障类型是否正确。故障类型间存在因果邻近（例如慢 SQL 与下游超时）、混淆（例如内存泄漏与 OOM Kill）、同簇（例如同属依赖故障）三类关系，若将不同性质的误判等同处理将丢失评估信号。RCA-Bench 在故障类型目录上定义一张有向图（节点为故障类型，边携带关系类型），Agent 输出在该图上寻找与基线真值的最短语义距离，距离越近部分分越高，五个匹配等级见表 5-4。

5.2.2 Boundary Score（定界评分）

定界评分衡量 Agent 所定位实体与真实根因的距离，依据 UModel 拓扑图距离而非字符串相似度。距离量化为拓扑跳数，距离越近部分分越高，七个匹配等级见表 5-5。

5.2.3 Process Score（过程评分）

过程评分检验 Agent 到达结论的行为路径：证据是否充分、因果方向是否正确。定因与定界考察诊断结果，过程考察 Agent 抵达结果的行为路径，用于防范概率性正确。Agent 可能因概率匹配或模式记忆恰好给出正确答案，但未查关键证据、也未沿因果方向推理；此类正确性在生产环境中不可复现。过程分由三个独立子维度加权构成，见表 5-6。

§5.3 图结构评分与 LLM 评判比例

评分协议遵守以下规则。其一，评分须分解为确定性与 LLM 评判两部分；二者权重比例须显式量化并作为评分协议的公开属性 commit。其二，确定性部分须基于第 4 章给出的两张图结构（故障类型拓扑、实体传播拓扑）以规则计算，不得引入 LLM 评判。其三，LLM 评判部分仅承担规则无法覆盖的过程接地判断；评判用量比例（当前 RCA-100 v1 为 18%）须在 release notes 中声明，跨版本变更视为 breaking change。

5.3.1 设计原则与两张拓扑图

设计原则为确定性优先：尽可能采用确定性规则评分，仅在规则无法覆盖的维度引入 LLM 评判。若评分大部分依赖 LLM，即由一个模型判定另一个模型输出"是否大致正确"，评估本身将成为不可控变量；更换评判模型时同一输出的得分可能波动 10% 以上且无法解释。RCA-Bench 通过两阶段工程降低评判依赖。

评估协议在工程实践中的首要要求是能在配置差异处给出稳定可区分的综合分。若协议对配置调优、模型升级、工程路径三类干预均不敏感，评估结果只能用于判断 Agent "是否能跑通"，不能用于判断"哪个配置更值得部署"。本节在 RCA-100 30 用例分层评估子集（n=30）上把上述三类干预拆为可对比的 Agent 配置矩阵实测综合分跨度：三个跨度分别为 10.07 分、5.25 分、13.36 分，均显著高于评估协议自身的评判噪声（σ\_intra 约 1.65 分）。

6.1.2 实验结果

§6.2 三维正交性的实测验证

6.2.1 实验设计

验证在 n=2,900 trial 的累积评分数据上展开，数据来自质量门禁重复评分实验 1,388 trial、主实验 1,477 trial、跨模型对照 35 trial，覆盖 5 个 Agent 框架与 6 个 LLM 系列共 28 个配置单元。28 个配置单元既包含主榜上的高分组合（如 deepseek-v4-pro + 调优配置）也包含尾部弱基线（如 react + paas 默认配置），使两项判据在配置能力跨度上得到压力测试。

6.2.2 实验结果

正交性方面，三维 Pearson 相关系数为 boundary-process 0.437、cause-process 0.414、cause-boundary 0.268（n=2,900 trial），三对均显著低于 0.7 阈值，相关性矩阵详见图 6-3。三维实测正交，cause-boundary 对的相关性最低（0.268），cause 维度的离散分类语义与 boundary 维度的拓扑距离语义不可互相替代；boundary-process 对相关性最高（0.437）但仍远低于阈值，反映"定位精度"与"调查路径合理性"之间的天然耦合可被独立信号区分。

6.2.3 结论

两项判据均成立。正交性方面，三对 Pearson 相关系数（0.268、0.414、0.437）均显著低于 0.7 阈值。必要性方面，boundary 消融后 Kendall τ 0.836 跨过 0.85 失真线，主榜不可去除 boundary 维度；cause 与 process 消融的 τ（0.937、0.968）在当前 n=28 cell 上未跨过失真线，但两者各自承担与 boundary（定位 + 归一）质性不同的诊断信号——cause 提供离散故障类型分类、process 提供调查行为路径合理性——三维分解的方法学价值由此体现：单维通过率将一条用例折算为 0 或 1 的二元通过失败，对部分正确诊断（如故障类型正确但根因实体定位至同 deployment 的兄弟 Pod）无法给出区分信号；三维分解可分别在 cause 给出 EXACT 命中、在 boundary 给出 SAME\_RUNTIME\_GROUP 命中（0.80 部分分）、在 process 按行为路径合理性独立打分。该区分能力是 RCA 任务的固有需求——生产环境中 SRE 对 Agent 输出的判定非二元通过失败，而是按"故障类型是否对、根因实体是否落在可操作粒度、推理过程是否可信"三项独立评价。三维评分函数定义见 §5.2。

§6.3 结构化基线真值与 UModel 跨域归一的复现性

设计二的实测有效性依赖两项条件：UModel 五步归一管线相对字符串匹配存在显著命中率优势；C0 至 C3 链位置编码能区分不同链位置命中样本对应的综合分。第一项不成立时，跨域实体归一退化为字符串相似度匹配，评分公平性受 Agent 输出文本表达差异主导而非语义差异主导；第二项不成立时，链位置编码沦为标签噪声，三维评分无法捕获 Agent 沿因果链回溯的程度差异。本节在 30 用例评估子集上分别给出实测：UModel 命中率 66.7% vs Levenshtein 6.7%（跨度 60 百分点），C0 vs miss 综合分跨度 29.5 分（71.93 vs 42.42）。

§6.4 LLM 评判部分的评分方差

设计三的实测有效性依赖一项条件：LLM 评判子项的方差对综合分整体方差的贡献低于预设 15% 安全线。该条件不成立时，LLM 评判方差吃掉真实的配置能力差异——同模型重复评判即可改变 Agent 排序，跨次评估结果不可比较，跨厂商评判方差更被放大。本节在 30 用例 × 5 重复评判（n=150 次评判调用）上给出实测：σ\_intra 1.65 分 / σ\_total 19.10 分，占比 8.6%，低于 15% 安全线 6.4 百分点。

6.4.2 实验结果

RCA-Bench 当前版本在数据集形态、实测覆盖与评估方法学三个层面仍有未尽工作。本节 10 项局限均为 RCA-Bench 内部努力可缓解的次级未尽工作，每条均有对应演进路径；须行业协作或方法学突破推进的开放命题另见下一节。

7.1.1 数据集形态层面的三类局限

数据集形态层面的三类已识别局限均与当前注入驱动路径直接相关，分别体现在故障并发度、与生产环境的差距、长尾故障覆盖三个方面，见表 7-1。

7.1.2 实测覆盖层面的三类局限

实测覆盖层面有三类局限，分别体现在评估子集规模、跨基准可比性与 Agent 集合广度三个方面。

7.1.3 评估方法学层面的四类局限

评估方法学层面尚有四类未尽工作，分别涉及评估对象的范式覆盖、评分函数参数的校准依据、LLM 评判的跨模型方差边界，以及多智能体审核机制的成熟度。

§7.2 开放问题

本节五项命题的解决路径部分须行业协作、部分须方法学突破，难度高于上一节内部可缓解的局限。五项按解决路径归为三类：外部对接类（外部判据引入、跨基准评分映射）、内部方法学类（合理但非专家路径边界、Agent 行为驱动数据生成）、治理类（开放性与防泄漏平衡）。

7.2.1 外部判据的引入

SWE-bench [5] 类基准的关键优势在于具备来自评估体系之外的客观判据：补丁通过 unit test 是与评估协议无关的独立信号。RCA Agent 评估目前缺少同类外部判据，所有评分都基于评估体系自身定义的基线真值与评分协议。如何引入类似的外部判据（例如 Agent 给出的修复建议执行后故障是否在生产环境复现、诊断结论是否被一线 SRE 在事后复盘中采纳），是 RCA 评估摆脱"自评自证"困局的关键方向。该问题的难点在于：外部判据本身的获取成本高，须依赖生产环境与 SRE 协作；且不同生产环境的判定标准存在差异，难以做跨基准对照。

7.2.2 合理但非专家路径的边界

过程评分当前判定的是 Agent 推理是否合理，但 SRE 实际诊断中常存在多条合理路径：经验丰富的 SRE 可能跳过部分中间证据直接定位根因，经验较少的 SRE 按完整流程逐步排查，两条路径的结论与诊断质量可能均正确。如何在评分中区分"非专家路径但合理"与"反向因果错误"，是过程评分的方法学难点。当前 Directionality 子维度的判定依赖 LLM 评判的语义分析，把这一边界留给评判模型的主观判断；跨模型的判定一致性面临相应方差挑战，方差降低路径与多智能体审核演进直接关联。

7.2.3 Agent 行为驱动与故障类型驱动的数据生成

当前数据集扩展沿故障类型维度展开，按 6 大类 40 余种故障类型逐步补充样本。更深层的扩展方向是 Agent 行为驱动：根据 Agent 在现有数据集上的失败模式反推应补什么样的新用例，使数据集设计与 Agent 能力进化同步。两条路径并不互斥（故障类型驱动保证覆盖广度，Agent 行为驱动保证压力测试有效性），但二者的优先级与权衡尚无行业共识。当前故障样本扩展暂以故障类型驱动为主，Agent 行为驱动的补充机制属于后续演进方向。

7.2.4 跨基准评分映射的语义稳定性

RCA-Bench、OpenRCA、AIOpsLab、Cloud-OpsBench、SREGym[21] 等同代基准各自给出 Agent 综合分时，跨基准可比性的建立目前尚无统一方案；是否存在一套可在多个基准间转换的语义稳定评分映射，仍是开放命题。该问题的解决须经行业级协作推进，无单一基准方能独立完成。一种可行的中间方案是建立"基准间的 calibration set"，即少量高质量公共用例同时在多个基准上评分，作为跨基准评分映射的依据；该机制的运营须依托中立的评估社区或标准组织。

7.2.5 开放性与防泄漏的平衡

评估基准的开放性与基线真值防泄漏存在天然矛盾：开放使数据集可被外部审计、复用、扩展，亦使基线真值更容易被纳入模型训练语料，导致评估失真。在不泄漏基线真值的前提下向外部团队开放足够上下文以支持诊断过程的复现与审计，涉及评估协议、Private Track 机制与开源协作模式的综合设计。一种可行方向是公开用例的结构与字段定义而不公开基线真值的具体值，外部团队复现时使用与公开数据集同构但内容不同的 holdout 用例。

§7.3 未来扩展

六条未来扩展方向对应前两节列出的局限与开放问题，覆盖数据规模、评估协议、Agent 形态、训练闭环与行业生态五个方向。部分方向已在执行中。

7.3.1 从注入驱动到生产级评估

当前数据主要来自受控注入。下一阶段须延伸到生产级环境，两项核心挑战：脱敏（线上观测信号含敏感内容，须经完整脱敏与重写流程）与基线真值构造（线上根因须由 SRE 事后确认）。中间路线含三步：staging 环境复刻生产拓扑、生产灰度受控注入、对接线上 SRE 演练平台。真实事故 replay 是另一条平行路径。

7.3.2 故障样本扩展与流量校准方法学

数据集扩展按混淆对密度推进，确保每对表象相似但根因不同的故障类型有足够样本多样性，对应长尾故障覆盖局限。同步建设工程化基础设施（数据访问规范、license、citation、responsible use 说明）。流量校准方法学引入两类校准依据：生产工单反推业务角色真实流量分布、故障传播链长度统计校验时间压缩比率。

7.3.3 多智能体审核演进与 Private Track 治理

完整多智能体审核管线由多个独立 LLM 对每条用例做投票聚合，存疑用例进入人工复核。演进方向有三：模型组合优化（强模型负责正确性、弱模型负责覆盖）、审核 prompt 迭代（强化因果链方向性与证据接地判定）、审核置信度基线（与 SRE 双人共识长期校准与跨厂商方差实测）。Private Track 保留非公开 holdout 用例，防训练数据污染与检测排行榜过拟合。

7.3.4 Agent 形态演进与新型故障覆盖

RCA Agent 形态演进含三类范式扩展：CodeAct（输出可执行代码）、Reflection（自我反思修正）、Multi-Agent 协作；评估基准须为各范式扩展 process 评分子维度。同期覆盖多故障并发场景（突破单故障局限）与 LLM 原生故障（模型超时、RAG 为空、prompt 注入等）。长上下文 Agent（128K 至 1M token）的对照能力同样须新增。

7.3.5 从评估走向训练与诊断闭环

冻结快照模式下，用例、基线真值与评分协议三者构成可重放奖励信号，适配 SFT、DPO、RLHF 训练。再进一步是诊断与修复一体化，评估对象从"诊断结论"扩展到"诊断结论与修复动作"，对应外部判据开放问题。第三方向是持续校准：每月引入新故障样本后重新校验评分函数衰减参数、评判 prompt 鲁棒性与多智能体一致率基线。

§7.4 本章小结

本章给出 RCA-Bench 在当前阶段的边界与演进。10 项当前局限大部分由 RCA-Bench 内部努力可缓解，预计在未来两至四个月内随数据集扩充与评分协议迭代逐步收敛；5 项开放问题须依赖行业协作或方法学突破推进，无单一基准方能独立完成；6 条未来扩展方向锚定 RCA-Bench 从静态评估基准向演进型方法学方案的路径，覆盖数据规模、评估协议、审核机制、Agent 形态、训练闭环与行业生态六个方向。

附录 B：用例难度分级 L1 至 L4 二维框架

B.1 难度分级二维框架

难度沿两个独立轴度量：传播分 x（根因离告警的拓扑跳数）与诊断分 y（确认根因所需的异构信号种类数）。长链短查（x 高、y 低，如缓存击穿）与短链长查（x 低、y 高，如线程池耗尽）属两种独立的难度模式，单维框架会将两类折叠为中等难度。

B.2 103 条样本的难度分布与主导因素

当前 103 条合格样本的难度分布为：L1 约 10%、L2 约 40%、L3 约 45%、L4 约 5%，主战场集中于 L2 与 L3。基于该样本规模的统计观察，拉高难度的主要因素是检查点数量、信号稀疏性与混淆证据，传播链长度的影响相对有限。L1 至 L4 仅为数据集治理标签，并不代表绝对难度真值；同一用例对不同 Agent 的难度排序可能不同。
