# 与 STAROps 有效对话

<div class="sls-starops-article-meta">
  <span>分类 · 开始上手</span>
</div>

> 对话回放：[6 原则会话回放](/playground/effective-prompts-replay.html)

在 STAROps 中，提问方式会影响数字员工取哪些数据、调用哪些技能、关联哪些 UModel 实体。明确实体、时间窗、业务意图和期望输出，可以让数字员工更快收敛到可验收结论。系统慢这类笼统描述会扩大搜索范围，增加反复补上下文的成本。

有效对话是所有上层实践的入口能力。业务可靠性巡检、RDS 巡检、告警 RCA 和容量风险预测都依赖清晰的实体、时间窗、数据范围和输出要求。

## 六条对话原则

这 6 条原则依赖 STAROps 的三层支撑。离开 UModel、会话和技能，它们只会退化成泛化表达建议。

| 支撑层 | 作用 |
|---|---|
| UModel（可观测模型） | 解析实体和关系，把服务、接口、实例、日志、指标和拓扑关联起来。 |
| 会话（Thread） | 在同一会话内保持上下文连续、一致；对话变长后用 `/compact` 压缩，保留要点继续多步分析。 |
| 技能（Skill） | 按任务选择技能，按它声明好的固定流程完成特定任务。 |

## 原则一：指定实体

支撑层：UModel 实体解析。

服务名、实例 ID、应用名和时间范围都是 UModel 可解析的对象。实体明确时，数字员工可以跳过对象猜测，直接围绕目标实体取数和关联证据。

| 类型 | 示例 | 说明 |
|---|---|---|
| 不推荐 | `帮我看下系统最近怎么样` | 搜索范围过宽，容易选错实体。 |
| 推荐 | `@checkout 给出当前实体的健康总览：近 24 小时核心指标（QPS、错误率、平均延迟、实例数）、近 24 小时告警次数与最严重告警、关联的上下游服务列表。` | 通过 `@checkout` 锁定实体，并声明指标和时间窗。 |

## 原则二：使用业务意图

支撑层：UModel 实体可查询 + 数字员工意图转换。

使用业务意图描述目标。PromQL、SQL 和过滤表达式由数字员工基于可查实体处理。这条原则依赖 UModel 实体可查和数字员工的意图转换能力，不依赖技能。

| 类型 | 示例 | 说明 |
|---|---|---|
| 不推荐 | `sum(rate(http_requests_total{service="checkout",status=~"5.."}[5m])) by (instance)` | 用户把查询语法写死，容易脱离 STAROps 实体上下文。 |
| 推荐 | `@checkout @inventory 对比 3 小时前与 1 小时前这两个时间点最近半小时内，平均延迟、错误率、QPS 的差值，标出变化超过 20% 的指标。` | 用业务对象、时间窗和判断规则表达目标。 |

## 原则三：保持同一会话（Thread）

支撑层：会话（Thread）上下文管理，包括连续、一致和压缩。

每个会话（Thread）是数字员工的一段工作上下文。多轮对话保持在同一会话内，数字员工可以复用前轮结论；新开会话等于重新开始。

| 能力 | 说明 |
|---|---|
| 连续 | 同一会话内实体上下文跨轮累积。 |
| 一致 | 前后结论可引用，前轮确认的实体和判断不会断链。 |
| 压缩 | 对话变长后用 `/compact` 压缩上下文，保留要点，适合承载多步分析。 |

| 类型 | 示例 | 说明 |
|---|---|---|
| 不推荐 | 在新会话提问 `刚才那个慢查询继续看下应用层` | 新会话没有前序上下文。 |
| 推荐 | `基于上面的 checkout 健康总览，关联最近 1 小时 checkout 下游 payment、cart、shipping 的错误率，定位哪个下游异常可能影响了 checkout。` | 在同一会话内复用前序结论。 |

涉及业务服务可靠性巡检、告警 RCA、多跳关联等多步分析时，应在同一会话内连续推进；新开会话后，需要重新提供前序结论。

## 原则四：声明输出形态

支撑层：数字员工的输出形态约束。

在提问末尾写清期望产出，让数字员工直接给出可验收结论。输出形态不明确时，数字员工容易返回大段叙述，用户还要二次整理。

| 类型 | 示例 | 说明 |
|---|---|---|
| 不推荐 | `分析下这个服务的健康状况` | 输出范围和验收标准不清。 |
| 推荐 | `@frontend 近 1 天内 [Health Rule] request_rate_compare 触发了多少次、平均存活时长、与 latency_avg_compare 的关联度；基于这些数据给出降噪建议（调阈值 / 调时间窗 / 合并规则 三选一并说明理由）。` | 明确指标、时间窗、输出字段和决策选项。 |

## 原则五：补齐缺失数据

支撑层：UModel 拓扑残缺兜底。

当 trace 采样率低、告警未接入或拓扑不完整时，数字员工可能只能画出残缺关系。把已知依赖补在提问末尾，可以让数字员工优先采用这些背景，并合并实时发现的额外依赖。

| 类型 | 示例 | 说明 |
|---|---|---|
| 不推荐 | `给我画出 checkout 的依赖拓扑` | trace 不全时，结果可能缺失依赖且不提示缺口。 |
| 推荐 | `画出 @checkout 的依赖拓扑。已知下游依赖：checkout -> cart、checkout -> payment、checkout -> shipping、checkout -> inventory、checkout -> currency、checkout -> email、checkout -> flagd。如在 trace 中发现额外依赖请合并。` | 用已知依赖兜底 UModel 拓扑缺口。 |

## 原则六：显式调用技能

支撑层：技能（Skill）调用。

业务技能有两个入口：输入 `/skill` 从列表里选择，或者在提问中点名要用的技能，再按提示补充上下文。走技能入口会进入它声明好的执行流程，执行更稳定，输出更结构化。

| 类型 | 示例 | 说明 |
|---|---|---|
| 不推荐 | `帮我巡检下 RDS` | 数字员工可能走通用排查路径，或反复要求补上下文。 |
| 推荐 | `/skill` 选择调用链诊断，补充 traceId | 通过技能入口锁定执行流程。 |

当 traceId、告警 ID 或任务 ID 等唯一定位 ID 已存在时，时间窗和数据源可以省略，ID 会锁定上下文。

技能管理需要专业版及以上订阅；系统内置员工不支持技能管理。

## 两个会话级设置

同一句提问在不同会话里效果不同，常常与两个设置有关。

**默认规则**按角色定义、数据源聚焦、分析逻辑约束、输出要求四部分编写，约束数字员工怎么分析和输出；改动只对后续新建的会话生效。配置方法见[《配置默认规则》](https://help.aliyun.com/zh/starops/user-guide/configure-default-rules)，生效范围见[《常用名词》](https://help.aliyun.com/zh/starops/product-overview/core-concept)。

**模型选择**默认是 Auto，也可以手动选 Qwen、GLM 或 DeepSeek；所选模型下线时，会话自动切回 Auto。可选范围和切换规则见[《选择模型》](https://help.aliyun.com/zh/starops/user-guide/select-model)。

怀疑同样的提问这次答得不一样时，先看这两个设置有没有变。

## 提问模板

以下模板用于常见 STAROps 对话场景。

**单服务健康检查**

```text
@<服务名> 看最近 <时间范围> 的 <指标列表> 是否偏离 <基线>，
偏离的指标按严重程度排序，并给出是否需要立即介入的判定。
```

**跨服务影响分析**

```text
基于上面的 <前序结论>，关联 <下一层数据范围>，
定位哪些 <实体类型> 异常可能影响 <业务指标>。
```

**调用既定技能**

```text
/skill 选择 <技能名>，按提示补充 <对象或 ID>。
要求：<输出格式 / 分级 / 附加字段>。
```

## 常见问题

### 提问越长越好吗

长度应匹配任务复杂度。单一查询一句话即可，多步骤分析需要写明产出形态和兜底信息。冗长提问会让数字员工在无关条件上过度匹配。

### 不知道准确服务名怎么办

先在数据建模的实体列表或 `@` 候选里确认名称，再写入提问。同名对象较多时容易选错，宁可先确认再提问。

### `@` 提及有什么区别

`@<服务名>` 是 STAROps 的实体提及语法，直接绑定到 UModel 中的对应实体。数字员工后续的指标查询默认在这个实体范围内。多个同名服务时，从 `@` 候选里选准目标，避免落到别的对象上。

### 何时显式分 Phase

简单场景可以让数字员工自由分析。复杂场景，如业务服务可靠性巡检和告警 RCA，建议显式分 Phase，每个 Phase 都明确输入、输出和停止条件，便于复盘和归档。

### 输出和预期不一致怎么办

在同一会话内要求数字员工调整输出形态。它会基于已有上下文重新组织结果，不需要新开会话重复前序问题。
